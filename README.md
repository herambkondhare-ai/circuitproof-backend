# CircuitProof

**Describe a circuit in plain English, get a verified KiCad schematic.**

CircuitProof turns a request like *"ESP32 with an MPU-6050 IMU on I2C and a status LED, powered from 5 V via an
AMS1117-3.3"* into a native KiCad schematic (`.kicad_sch`) plus an audit report. NVIDIA Nemotron proposes the
design; deterministic code completes and checks it; KiCad's own ERC confirms it. Designs that fail are sent back
to Nemotron with the exact problems to fix. CircuitProof can also audit schematics it did not create.

```
prompt ─▶ part planning + search of all ~21,700 installed KiCad symbols
       ─▶ Nemotron proposes a netlist (JSON)
       ─▶ deterministic completion: fixes pin names, power wiring, pull-ups, decoupling, crystals, LEDs ...
       ─▶ referee rules + KiCad ERC (kicad-cli) on a draft schematic
              ▲                                       │ problems found
              └─────── exact problems fed back ───────┘ (repair rounds, within a time budget)
                                      │ accepted
                                      ▼
                     .kicad_sch  +  audit report (.md)  +  KiCad ERC result
```

## Examples

Each folder in [`examples/`](examples) holds a design generated by CircuitProof from the prompt shown, with the
KiCad schematic, a picture of it exported by KiCad, and the audit report. All of them were accepted by the
referee with **0 KiCad ERC errors**.

| [02_esp32_imu](examples/02_esp32_imu) | ESP32-WROOM-32 with an MPU-6050 IMU on I2C, a push button on IO0 and a status LED, powered from +5V via AMS1117-3.3 |

## What it does

- **Real parts and real pins.** Every symbol and pin comes from the KiCad libraries installed on your machine;
  multi-unit parts (dual op-amps, logic gates) are placed unit by unit.
- **Generate → verify → repair.** Each design is checked by the rule referee *and* by KiCad's ERC before it is
  accepted. Problems go back to Nemotron as precise instructions.
- **Deterministic completion.** The model's frequent slips are fixed in code and listed in the report, for
  example: `SDA` written for a chip whose pin is `IO21`, a ground pin on a signal net, missing I2C pull-ups or
  decoupling capacitors, an unwired regulator input, a sensor on the wrong voltage rail, a requested crystal that
  was left out, a status LED with no driver, or a resistor that was listed but never connected.
- **Live progress.** The studio shows the current stage ("Designing netlist · 12s") while a design is generated
  in the background.
- **Honest reports.** Every finding is PASS, FAIL, WARNING or NOT EVALUATED. Missing datasheet data is reported
  as NOT EVALUATED, never guessed; every automatic fix is listed in the repair history.

## Setup (Windows)

1. Install **Python 3.10+** and **KiCad 8 or newer**. KiCad provides the symbol libraries and `kicad-cli`;
   CircuitProof finds both in the default install folder.
2. Install the dependencies from the repository root:
   ```
   pip install -r backend/requirements.txt
   ```
3. Configure Nemotron. Get a free API key at build.nvidia.com, then run once:
   ```
   setx CP_LLM_PROVIDER "nvidia"
   setx CP_LLM_MODEL "nvidia/nemotron-3-nano-omni-30b-a3b-reasoning"
   setx CP_LLM_API_KEY "nvapi-..."
   ```
   Open a **new** terminal afterwards. Never commit API keys. To use a local model instead, set
   `CP_LLM_PROVIDER=ollama` and `CP_LLM_MODEL` to your Ollama model tag.
4. Test and start:
   ```
   python backend/app/selftest.py
   python run.py
   ```
5. Open http://127.0.0.1:8000 for the studio. http://127.0.0.1:8000/api/health shows whether the model, the
   KiCad symbols and `kicad-cli` were found; http://127.0.0.1:8000/docs lists the API.

### Optional settings

| Variable | Default | Meaning |
| --- | --- | --- |
| `CP_LLM_THINKING` | `off` | `on` lets Nemotron reason before answering: better on hard designs, but minutes per round |
| `CP_GEN_BUDGET_S` | `180` | time budget for one generation; when it runs out the best design so far is returned |
| `CP_LLM_TIMEOUT` | `90` | maximum seconds for one model call |
| `CP_LLM_RETRIES` | `2` | retries for a busy model endpoint (HTTP 429/503) |
| `CP_LLM_HEDGE_S` | `35` | if the model has not answered by then, the same request is sent once more in parallel |
| `CP_SYMBOL_DIR`, `KICAD_CLI` | auto | KiCad symbol folder and `kicad-cli.exe`, if KiCad is installed somewhere unusual |

## Try it

Prompts that name their main parts work best, for example:

- `ATmega328P with a DS3231 real-time clock on I2C with a coin cell backup battery and an LED`
- `STM32F103C8 on +3V3 with an 8 MHz crystal, an MCP2551 CAN transceiver on +5V and an AMS1117-3.3 regulator`
- `ESP32-WROOM-32 module on +3V3 from an AMS1117-3.3 regulator fed by +5V, with a BME280 sensor on I2C and a status LED`

A generation usually takes 30 seconds to 3 minutes, depending on how busy the model endpoint is. The studio's
**Verification Center** lists every finding; **Download .kicad_sch** saves the schematic.

## Results

Measured on this codebase with `nemotron-3-nano-omni-30b-a3b-reasoning` (thinking off) through NVIDIA's free API:

- On a set of 8 harder prompts (ESP32 / STM32 / ATmega / RP2040 boards with sensors, displays, flash, CAN,
  RTC and regulators), every design that came out passed with **0 KiCad ERC errors**, and each prompt produced
  a verified design in at least one recent run, typically in 30–170 seconds.
- Failed runs were almost always the model endpoint not answering in time (HTTP 504), not a wrong design.
- On prompts unlike anything tested (vague requests, unfamiliar parts), results are much weaker; see
  *Limitations*.

## API

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/api/health` | model, KiCad symbols, symbol-index progress, `kicad-cli` and generation status |
| POST | `/api/generate-jobs` | start a generation in the background; returns a `job_id` |
| GET | `/api/generate-jobs/{job_id}` | `status` (queued/running/done/error), current `stage`, `elapsed_s`, and the result when done |
| POST | `/api/generate-from-prompt` | the same generation as one blocking request |
| POST | `/api/verify` | re-run the referee on the design shown in the studio |
| POST | `/api/audit-design` | audit a design given as JSON (no model or KiCad needed) |
| POST | `/api/audit` | audit an uploaded `.kicad_sch` (needs `kicad-cli`) |
| GET | `/api/symbols/search?q=` | search all installed KiCad symbols |
| GET | `/api/components`, `/api/components/{id}`, `/api/parts` | parts with electrical facts |
| GET | `/api/schematic/{file}`, `/api/report/{file}`, `/api/files/{file}` | generated files |

Errors: 422 design problem (details in the body), 502 model request failed, 503 KiCad libraries or `kicad-cli`
missing, 504 no valid design within the time budget.

## Referee rules

- **Supply:** supply pins on a rail within the part's allowed range, never tied to ground.
- **Ground:** ground pins on a ground net; IC power pins must be connected.
- **Decoupling:** a capacitor to ground for each supply pin of each IC.
- **I2C:** a pull-up on each line within the parts' voltage limits; no pull-downs; duplicate pull-ups flagged.
- **SPI:** the declared clock is within each device's limit.
- **Connectivity:** nets that reach only one pin.
- **Part data:** ICs without facts in the knowledge store are listed as NOT EVALUATED.

On top of the rules, a design is only accepted when KiCad's ERC reports no errors and every resistor, capacitor,
LED and crystal is connected at both ends.

## Limitations

- **"Accepted" means the design passes the electrical checks above, not that it does what you meant.** The
  referee cannot judge whether the chosen parts and topology suit the purpose: in testing, a "microphone preamp"
  came out as an op-amp with no feedback network (a comparator), with 0 ERC errors. Review every design and the
  datasheets before building hardware.
- **The model is the weakest link.** With thinking off, Nemotron Nano is fast but sometimes repeats the same
  mistake through all repair rounds, mainly on vague prompts or unfamiliar parts. Naming the main parts in the
  prompt helps a lot.
- **The free API endpoint is sometimes overloaded** and may not answer within the time budget. Try again, or
  raise `CP_GEN_BUDGET_S`.
- **Few parts have datasheet facts.** Supply ranges exist for 13 common parts, all unverified seed values in
  `backend/app/load_components.py`; voltage rules for other parts report NOT EVALUATED.
- **The rule set is focused.** There are no checks yet for crystal load capacitance values, reset circuits,
  MOSFET gate drive, current or power ratings, analog signal levels, USB data lines or ESD protection.
- **Automatic fixes are rules of thumb** (for example, a regulator without an input rail gets +5 V). Each one is
  listed in the report's repair history so it can be reviewed.
- One A4 sheet per design, parts connected by net labels, one generation at a time, and jobs kept in memory only.

## Project structure

```
├── run.py                       one-command launcher (API + studio on :8000)
├── examples/                    generated designs: schematic, SVG picture, report, prompt
├── frontend/
│   ├── index.html               web studio (served by the backend)
│   └── public/                  favicon, social image, robots.txt, sitemap.xml
└── backend/
    ├── requirements.txt
    ├── app/
    │   ├── main.py              FastAPI app: API, background generation jobs, serves the studio
    │   ├── planner.py           Nemotron generate → complete → verify → repair loop
    │   ├── llm_client.py        NVIDIA API / Ollama / any OpenAI-compatible endpoint (retries, hedging)
    │   ├── symbol_index.py      searchable index of all installed KiCad symbols (built in a separate process)
    │   ├── design.py            the design format every module shares
    │   ├── circuitproof_core.py deterministic rule referee
    │   ├── generator.py         KiCad schematic writer (real symbols, real pin positions, all units)
    │   ├── scan_project.py      reads existing .kicad_sch via kicad-cli, runs KiCad ERC
    │   ├── knowledge_store.py   SQLite: part facts, symbol mappings, mistakes
    │   ├── load_components.py   seed parts (added automatically at start)
    │   ├── report_exporter.py   Markdown audit report
    │   ├── timing.py            [timing] logs and generation stages
    │   ├── ui_compat.py         shapes results for the studio
    │   └── selftest.py          offline tests
    ├── demo/                    buggy_i2c.json (planted bugs), good_i2c.json (fixed)
    ├── data/                    SQLite database and symbol index cache (created automatically, not committed)
    └── exports/                 generated schematics and reports (not committed)
```

The server prints `[timing]` lines for every stage (model calls, symbol search, referee, ERC), which show where
the time of a generation goes.
